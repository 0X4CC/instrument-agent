## 一、目标架构

```
                     用户 / 平台访问
                          │
                          ▼
              ┌───────────────────────────┐
              │      运维调度 Leader       │
              │  意图解析 · 并发分派 · 聚合 │
              └─────────────┬─────────────┘
                            │ AIP 协议
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
 ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
 │  状态采集     │   │   故障诊断    │   │  维护资源     │
 │  Partner     │   │   Partner    │   │  Partner     │
 │ 【异构适配层】 │   │  规则推理     │   │ 手册/工单/备件 │
 └──────────────┘   └──────────────┘   └──────────────┘
```

**核心思想**：**各厂商仪器的"方言"被隔离在 Partner 内部，AIP 层看到的是统一的能力。**

新增仪器类型 → 加一个采集适配器 → **Leader 零改动**。

### 并发编排实测（开启 200ms 模拟仪器通信延迟）

| 阶段 | 串行 | 并发 | 加速 |
| --- | --- | --- | --- |
| ① 状态采集（4 机组） | 856.8 ms | 250.9 ms | **3.4×** |
| ② 故障诊断（9 台） | 36.5 ms | 29.5 ms | 1.2× |

**现在的 `diagnose.py` 就是未来「故障诊断 Partner」的核心逻辑**——只是还没包协议壳。

## 三、诊断逻辑

### 3.1 三级判断

```
读仪器状态
   │
   ├─ 没有错误码 ──────────────────► 正常
   │
   ├─ 错误码不在规则库 ────────────► 未知故障（转人工）
   │
   └─ 错误码匹配到规则
         │
         ├─ 传感器数据佐证 ────────► 确诊
         └─ 传感器数据不支持 ──────► 疑似（可能是误报）
```

### 3.2 为什么要有"疑似"

**仪器报了错，不代表真的坏了。**

例：分光光度计报 `E-302`（基线漂移超限），但实测基线漂移只有 `0.003`，阈值是 `0.005`。
**上报了错误码，但数据不支撑。**

- **死规则**：看到 `E-302` 就报"基线漂移"，让人白跑一趟
- **本系统**：判为"**疑似**"，并列出"哪个数据没佐证"

> **这就是"诊断"和"查表"的区别。**

### 3.3 数据结构

一条故障规则长这样：

```json
{
  "code": "E-201",
  "device_type": "离心机",
  "name": "转子不平衡",
  "severity": "中",
  "checks": { "vibration_mm_s": 5.0 },
  "cause": "转子配重不均，或离心管放置不对称",
  "action": "停机，检查转子配重块与离心管对称性",
  "manual": "§3.2 转子平衡与维护"
}
```

| 字段 | 作用 |
| --- | --- |
| `code` + `device_type` | **匹配键**——同一错误码在不同设备上含义可能不同 |
| `checks` | **佐证条件**：传感器值 > 阈值才算数 |
| `severity` | 低 / 中 / 高 / 紧急 |
| `cause` / `action` / `manual` | 给人看的：为什么、怎么办、查哪儿 |
