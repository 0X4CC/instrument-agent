# 演示脚本（3 分钟）

> **目标**：让评委在 3 分钟内看懂"这是什么、解决什么问题、技术含量在哪"。
>
> 最后更新：2026-10-27

---

## 一、演示前 5 分钟准备

**开四个终端，都先 cd 到项目目录**：

```bash
cd "D:/Privacy Docs/study/agent/instrument-agent"
```

**终端 ①②③ —— 三个 Partner**（每个一个终端）

```bash
# 终端 ①：故障诊断（8011 对外，与 acs.json 的 endPoint 一致）
uv run uvicorn partners.main:app --port 8011

# 终端 ②：状态采集
PARTNER_LATENCY_MS=200 uv run uvicorn partners.status_server:app --port 8012

# 终端 ③：维护资源
PARTNER_LATENCY_MS=200 uv run uvicorn partners.resource_server:app --port 8013
```

> `PARTNER_LATENCY_MS=200` 是**模拟仪器通信延迟**（真实串口/Modbus 通常 100–500ms）。
> **不加也有结果，只是并发优势不明显。演示时建议加上，并如实说明是模拟。**

**终端 ④ —— 跑 Leader 命令（先空着）**

**浏览器**开一个标签页：

- `http://127.0.0.1:8011/docs` ← 诊断服务的接口文档

> ⚠️ **如果时间紧，只讲并发编排（终端 ④）也能讲完**——那是全场最值钱的 30 秒。

## 二、3 分钟流程

### 0:00–0:30　开场（讲问题，不碰电脑）

> "实验室的仪器出故障，现在靠三样东西排查：老师傅的经验、翻纸质手册、查故障码表。
> **问题有三个**：经验留不下来、响应慢、不同厂商的数据格式完全不通用。
>
> 我做的是把这件事变成**可执行、可复现、可被别人调用**的能力。"

---

### 0:30–1:10　第一层：诊断逻辑（看浏览器首页）

**点「巡诊全部」**

> "6 台仪器，一次巡诊，3 台确诊、1 台疑似、1 台未知。

> **注意这个「疑似」**——它报了错误码 E-302（基线漂移超限），
> 但我们实测基线漂移只有 0.003，阈值是 0.005。**数据不支撑这个报警。**
>
> 死规则的做法是：看到 E-302 就报'基线漂移'，让维修人员白跑一趟。
> **我的做法是判为「疑似」，并告诉你哪一项数据没佐证。**
>
> **这就是「诊断」和「查表」的区别。**"

> 再点一台，展示单台的详细结论（故障 / 严重度 / 依据 / 处置建议 / 手册章节）。

---

### 1:10–1:40　第二层：接口层（切到 /docs）

> "诊断能力已经封装成标准 HTTP 接口，5 个端点。
> **任何人、任何语言都能调**——`/diagnose` 传一个仪器编号，返回结构化 JSON。"

**在 `/docs` 里点开 `GET /diagnose`，填 `CEN-01`，点 Execute。**

> 展示：请求 URL + 返回的 JSON。

---

### 1:40–2:30　第三层：三 Partner 并发编排（切到终端 ④）⭐ **全场最值钱**

> "但真正的关键是：**它不是一个服务，是四个智能体在协作。**"

**在终端 ④ 跑**：

```bash
uv run python -m leader.main
```

**指着输出讲**：

> "看这个流程——**三阶段，每阶段内部并发**：
>
> 1. **状态采集 Partner** ← Leader 同时向 4 个机组要数据
> 2. **故障诊断 Partner** ← 对 9 台异常仪器并发诊断
> 3. **维护资源 Partner** ← 对 9 个故障码并发查手册和备件
>
> **注意每个结果的状态：`awaiting-completion`。**
> Partner 干完活**不直接说'完成'**，要等 Leader 显式发 `complete` **验收**才算完。
> **这不是设计缺陷，是 AIP 协议故意的**——给 Leader 留一个"验收 / 打回"的机会。"

**然后跑串行版做对比**：

```bash
uv run python -m leader.main --serial
```

**指着两组数字讲**：

> "**串行 2853 ms，并发 511 ms，快 5.6 倍。**
>
> 但注意**阶段 2 几乎没提速**（36ms → 29ms）——因为它是纯计算，没有 IO。
>
> **并发只对'等 IO'有效。** 状态采集和维护检索要等仪器响应，所以加速 3.4 倍和 8.5 倍；
> 诊断是纯内存规则匹配，并发帮不上忙。
>
> **这是阿姆达尔定律的直接体现**——**并发不是万能的，要看瓶颈在哪。**"

> 💡 **这一段能同时证明三件事**：多智能体协作、AIP 协议语义、并发性能分析。
> **评委问"多智能体的价值在哪"，这一屏就是答案。**

---

### 2:30–3:00　收尾（讲价值）

> "总结三点：
>
> 一，**规则推理不依赖大模型**——结果确定、可复现、不花钱、断网也能跑。
>
> 二，**三级判断**（确诊 / 疑似 / 未知）比"查表报错"更接近真实运维。
>
> 三，**能力已经封装成标准智能体**——别的系统可以通过协议发现它、调用它，
> 而不需要知道里面是怎么实现的。
>
> **这就是「异构隔离」**：仪器换厂商、换型号，**Leader 一行代码都不用改**。"

## 三、如果被追问（准备这 5 个答案）

| 问题 | 怎么答 |
| --- | --- |
| **数据是真的吗？** | "目前是**构造数据**（6 台仪器 / 11 条规则），结构按真实故障码表设计，接口已预留，拿到实验室数据直接替换 `data/` 下两个 JSON 即可。" |
| **为什么不接大模型？** | "运维诊断要的是**可解释、可复现**。同样输入必须给同样输出，而且要说清'凭什么这么判断'。规则引擎满足这两点，大模型不保证。" |
| **多智能体的价值在哪？** | "**能力可被发现和组合**。以后加一台新型号仪器，只要按同样的 ACS 描述注册一个新 Partner，Leader 完全不用改。" |
| **性能怎么样？** | "单台诊断 **0.004 毫秒**（2000 轮循环取平均），纯内存规则匹配，没有网络和 IO。" |
| **平台验证做了吗？** | **如实说**："本地双进程链路已跑通（`start → awaiting-completion → complete → completed`），**平台注册正在进行中**。" |

> 🔴 **绝对不要说"已经在平台完成验证"**——没做的事不能说。
